Дата: 12 октября 2026 года. Выполнен независимый аудит полного перенесенного текста. Файл интегрирован основным агентом после сопоставления результатов продуктового и технического анализа.

Этот аудит проверяет состав спецификации. Точность переноса отдельно проверена сравнением TXT с JSON и производных разделов/промптов; результат — [verification.json](../verification.json). Ни одна из этих проверок не доказывает работоспособность приложения или актуальность внешних источников.

## 2. Границы приемки

Первый показ P22/A55–A58 должен быть работающим серверным демо:

1. Вымышленный салон, воспроизводимые seed/reset и постоянная отметка демо.
2. Запись через отдельные услуги и комплекс, с последовательными и допустимыми параллельными этапами.
3. DEMO-OTP, без реального SMS; атомарное подтверждение доступных ресурсов.
4. Администратор видит визит, переносит, фиксирует приход и передает мастеру.
5. Мастер сохраняет выполнение и подтверждает нормы либо отклонения расхода.
6. Закрытие сохраняет итог/методы внешнего расчета, материалы и предварительное начисление.
7. Мастер видит объяснение, владелец — расходы/выручку/результат, клиент — историю/рекомендации/сертификат или пакет/обратную связь.
8. Оператор видит демонстрационный реестр копий/версий без общей базы посетителей.
9. Роли проверяются через API; конфликт записи и повтор закрытия проверены.
10. Перезагрузка сохраняет серверное состояние; инструкция запуска и показ на 5–10 минут воспроизводимы.

Приложение только с localStorage не соответствует P22/A56. Создание публичной ссылки не блокирует разработку: пользователь организует ее самостоятельно.

Live требует реальных правил салона, инфраструктуры, OTP, импорта, безопасности, мониторинга и фактического восстановления. Отсутствие ИИ, gateway, медицинского или международного расширения не является дефектом отключенного этапа.

## 4. Найденные неоднозначности и решение основного агента

**G01 — число состояний.** P03 говорит о шести независимых статусах, I04 перечисляет семь независимых состояний. Сохранять все факты I04; количество бейджей интерфейса определять отдельно. Объединение UI-представления не объединяет состояния данных. Пользовательское решение для исправления счета не требуется.

**G02 — бесплатный хостинг.** A58 перечисляет сон, срок БД, эфемерные файлы и worker, тогда как P22 требует только фактических ограничений выбранной среды. Проверять применимость каждого ограничения; писать «не применяется», где его нет. Нельзя переносить характеристики Render на любую площадку.

**G03 — DEMO-OTP.** P15 допускает видимость test-кодов только dev, P22 требует демонстрационное подтверждение. Предложен отдельный demo-адаптер с серверной проверкой режима, явно вымышленными номерами и запретом live-кодов/реальных отправок.

**G04 — будущие сущности в общей модели.** PaymentIntent/Webhook из P02 явно исключаются его уточнением этапа 1. Это разрешенный самим источником случай; gateway не нужен для ручных расчетов.

**G05 — словарь людей/расчетов.** P04 требует Person отдельно от Account/Contact; P02 не закрепляет Person и имя основной ручной оплаты. Нужно описать словарь до схемы, сохранив I02/A09/A50.

**G06 — закрытие и ранее введенные факты.** Синхронность производных расчетов и переход от мастерского ввода к закрытию не заданы полностью. Обязательные факты должны быть согласованы; закрытие подтверждает/связывает введенное, а не повторно создает расход и выполнение.

Это дефекты/пробелы спецификации, а не найденные баги приложения: приложения еще нет.

## 5. Недостающие параметры по этапам

| Условие | Когда закрыть |
| --- | --- |
| Аудитория, услуги/комплекс, бренд, срок, принимающий и пожелания | До реализации демо |
| Seed и ожидаемые суммы/расходы/начисления/сертификат/исключения | При подготовке демо; значения явно вымышленные |
| Hold/OTP TTL, попытки и resend | Demo-значения записать; live согласовать по провайдеру и процессу |
| Округление/распределение копеек | До расчетов; политика явная |
| Событие/база начисления, период/область гаранта | Demo-пример обозначить; live согласовать |
| Признание сертификата дешевле номинала | До его расчетов; A52 условный |
| Отмена/неявка/перенос/возврат/переделка | Demo-пример обозначить; live согласовать |
| Метод склада/партии/отрицательные остатки | До рабочего склада |
| Нагрузка, RPO/RTO/SLO, браузеры/ответственные | До live и эксплуатационной приемки |
| Постоянная PostgreSQL/worker/хранение в среде показа | До показа |
| Несколько зрителей: общий стенд или независимые сеансы | До реализации демонстрационной среды |
| Стратегия обновления/rollback копий | До сопровождения нескольких live-копий |

Дополнительные границы будущих проверок: одновременные возвраты не превышают остаток; OTP при истечении hold не создает двойную бронь; расход при одновременном закрытии не теряется; переход суток учитывает локальный часовой пояс; мощность N имеет явную модель; погашение пакета проверяется отдельно от денежного сертификата; recovery не сводится к OTP на новом номере; лицензирование/поддержка имеют явную политику.

## 6. Как фиксировать фактическую приемку

Для каждого включенного сценария: требование → этап → данные → действие → ожидаемый результат → фактическое доказательство → статус → ограничения.

Пока приложение не реализовано, статусы A01–A59 — требования/запланировано, а не tested. В последующих отчетах разделять implemented, tested, not enabled и blocked; будущие расширения — planned. Наличие кнопки не доказывает действие; наличие тестового файла не доказывает его запуск.

Материальные UI-поведения проверять реальным браузером и скриншотами. Деньги, доступ и занятость — серверными запросами и настоящими транзакциями. Восстановление — практическим restore.

## 7. Внешние источники

Перенесены S01–S60 с URL. Не проверены их текущая доступность/содержимое, версии библиотек, тарифы/сервисы провайдеров, регионы БД/файлов/копий/логов, правовая применимость и Figma/ FigJam.

Пакет датирован 5 октября 2026 года. Утверждения исходника об исследовании не являются проверками этого проекта. Перед использованием нужно проверять актуальные первичные материалы по выбранным версиям и реально подключаемым сервисам; массовое повторное исследование всех внешних страниц не требуется для начала вымышленного демо.

## 8. Следующий шаг

Получить ответы по демо и пожелания → записать объем/seed/ожидаемые итоги → проверить версии и фактическое окружение → реализовать сквозной путь → проверить ресурсы/права/повторы и UX → подготовить воспроизводимый показ. Открытые live-вопросы сохраняются отдельно в [questions.md](../questions.md).
