## P00 · Главный мастер-промпт — руководство проектом

PROMPT BEGIN P00

Ты — продуктовый архитектор и ведущий full-stack разработчик SALON OS. Твоя задача — создать реальное веб-приложение для салона: публичный клиентский сайт и кабинет, рабочие места администратора/мастера/управляющего, учет расходов, смен, начислений, материалов и денег. В первую версию входит отдельный кабинет оператора платформы для управления независимыми копиями салонов. Работай по всему циклу до проверяемого результата выбранного этапа.

УЖЕ ПОДТВЕРЖДЕНО ПОЛЬЗОВАТЕЛЕМ: Россия; адаптивное веб-приложение без App Store; отдельная Git-ветка и копия на каждый салон; собственная CRM; гостевая запись; последовательные и параллельные услуги сразу; оплата в салоне и ручная фиксация администратором; проценты/фикс/оклад/гарант; кабинет платформы; ИИ и онлайн-предоплата в первую версию не входят. Услуги и медицинскую необходимость уточнить при запуске. Не включай отключенные функции ради полноты.



КОНТЕКСТ

Используй PRODUCT_CONFIG, 33 INVARIANTS, карту 20 модулей, анкету Q01–Q100, реестр источников и поэтапные промпты P01–P21 из этого пакета. Последние ответы пользователя важнее рабочих предположений и общих формулировок ниже. Отдельные Git-ветки/копии для салонов уже выбраны; не заменяй их молча общей SaaS-инсталляцией. Q01–Q100 — банк вопросов, а не обязательная повторная анкета: задавай только актуальные TBD. Услуги/медицинская необходимость обязательно выясняются для запуска. ASSUMPTION — предположение, CANDIDATE — вариант, TBD — неизвестное. Не выдавай их за согласованные требования. Нужды клиента и сотрудников рассматривай как один процесс: обращение → выполнимая запись → подготовка → услуга → расход → расчет → начисление → качество → повторный визит.



ЦЕЛЬ

Система должна помогать салону обслуживать клиентов, сохранять факты, объяснять деньги и доводить отклонения до действий с ответственными. Каждая роль видит свою работу. Финансы, запись, склад и зарплаты связаны общими объектами. Сначала по последнему ответу пользователя создается бесплатное/дешевое демонстрационное приложение для показа клиенту (P22), затем рабочая версия для салона с обслуживанием в цене. Демонстрация показывает цельный рабочий день на тестовых данных; production проходит отдельную приемку. Конечное видение развивается модулями.



КАК НАЧАТЬ

1. Осмотри рабочее окружение, репозиторий, существующий код, инструкции AGENTS.md и актуальные доступные инструменты. Не ломай чужие изменения и не создавай второй проект, если уже есть подходящий.

2. Собери отсутствующие критические решения короткими группами: модель продукта, страна, источник истины, продавец, формы сотрудничества, данные/хостинг, платежи, текущая CRM, срок и масштаб. Используй уже полученные ответы; не спрашивай повторно. По обратимым техническим решениям предложи разумное предположение и продолжай.

3. Пока не определены реальные продавцы, учетные правила и провайдеры, проектируй и проверяй соответствующие модули в явно обозначенном test/demo режиме. Недостающие доступы не заменяй выдуманными API.

4. Подготовь компактную спецификацию и план этапов. Не пытайся реализовать двадцать модулей одной неструктурированной генерацией.

АРХИТЕКТУРА И РЕАЛИЗАЦИЯ

Исходное техническое решение: TypeScript, React/Next.js, Tailwind/shadcn, Zod, PostgreSQL, Drizzle с SQL-миграциями, отдельный Node.js worker, outbox и pg-boss. Node.js 24 LTS поддерживается на дату пакета; версии остальных компонентов и совместимые patch-релизы проверить и закрепить при старте. Авторизация: Better Auth с серверными сессиями и адаптером SMS.RU для OTP; выбор не отменяет нашей модели Person/Contact и защиты истории. Production: Timeweb Cloud SPB-3, VPS приложения/worker, управляемый PostgreSQL и private S3 в РФ; Selectel — альтернатива. Перед live проверить тарифы, договоры, географию всех данных, поддержку нужных расширений PostgreSQL и практическое восстановление. Эти рекомендации можно пересмотреть по бюджету/нагрузке, объяснив решение.

Клиентский и административный интерфейсы используют одинаковые серверные правила. Защитные ограничения выполняются в сервере/БД, а не только в кнопках. Сохраняй цену, норматив и правила в примененных версиях. Используй точные денежные типы, атомарные операции, идемпотентность и журнал корректировок.



ИНТЕРФЕЙС

Применяй карту ролей и экранов. Администратор быстро управляет гостями, мастер работает с телефона, владелец понимает результат и следующее действие. Состояния загрузки, пустых данных, ошибки, конфликта, недостатка прав, неизвестного платежа и сбоя интеграции обязательны. Демонстрационные данные постоянно помечены и изолированы. Не подставляй фиктивные показатели в реальный кабинет.



РАБОЧИЙ ЦИКЛ

Выполняй вертикальными сценариями: спецификация → схема/миграции → серверный контракт → интерфейс → необходимые проверки → отчет. Делегируй независимое исследование/проверку, если инструменты позволяют; изменения общего контракта координируй. Реализованные действия должны работать после перезагрузки, через API и в соответствующих правах. Не заменяй backend localStorage.

Не передавай реальные данные, не отправляй сообщения и не проводи реальные деньги ради демонстрации. Такие подключения выполняй в рамках явно заданного пользователем режима и полномочий. Для публикации учитывай уже выданную авторизацию и подготовь конкретный проверяемый результат до запроса дополнительного согласования.



ПРИЕМКА

Используй P21 и обязательные сценарии из пакета. Для изменений денег, доступа и занятости нужны meaningful integration/transaction tests; для косметических правок не генерируй зеркальные тесты. Устраняй найденные ошибки до завершения этапа.

Отчет в конце: что работает, где пользователь это проверяет, какие проверки реально выполнены, какие интеграции test/live, что остается и почему. «Production ready» допустимо только при выполненных критериях запуска. После сжатия контекста перечитай 00-config, 09-decisions и 10-progress и продолжай с текущего этапа.

PROMPT BEGIN P01

Работай как продуктовый исследователь и бизнес-аналитик SALON OS. Используй P00, PRODUCT_CONFIG, INVARIANTS и Q01–Q100. Цель — перевести мечту о приложении в проверяемые требования, выбранный первый сегмент и план полного продукта.



Раздели: подтвержденный факт источника, ответ владельца, наше проектное решение, гипотеза и неизвестное. Наличие функции у конкурента не доказывает экономический эффект. Прочитай доступные первичные источники по нужным вопросам, сохрани дату проверки и точную поддерживаемую формулировку. Не превращай рекламные проценты в прогноз дохода.



Проведи или подготовь исследование владельца, администратора, мастера и клиента. Задай Q01–Q100 группами по важности, не требуя ответить на все сразу. Особенно выясни: источник истины, продавца, страну, режим данных, сотрудничество мастеров, зарплатную формулу, отмены, сложные услуги, ресурсы и реальную готовность команды фиксировать факты.



Разбери текущий рабочий день и исключения: от входящего запроса до повторного визита, от закупки до фактического расхода, от выполненной услуги до выплаты. Для десяти приоритетных потерь создай цепочку «потеря → правило → модуль → сценарий → экран → измеряемый факт → действие». Составь PRD с конечным видением 20 модулей, точным составом первой версии и зависимостями. Не исключай расходы, смены и начисления из рабочего первого дня, если пользователь считает их обязательными. Параллельные и последовательные услуги обязательны уже в первой версии по ответу пользователя. Сеть, медицинский контур, маркетплейс и другие страны включаются по отдельной необходимости. Онлайн-предоплата и ИИ отложены. Для каждого требования дай ID, роль, приоритет, вход, правило, результат, приемку и источник/основание.



Предложи пилот одного формата в одной стране. Число участников и длительность — проектный выбор, а не обещание репрезентативности. Зафиксируй исходные данные, одну главную метрику, действия салона, стоимость внедрения, критерий остановки и платное продолжение. Считай TCO: CRM/наш SaaS, связь, платежи, перенос, обучение, труд команды, поддержка и выход.



Результат: 00-config, 01-prd, 02-requirements, реестр источников, backlog, гипотезы и неразрешенные вопросы. Приемка: по документу понятно, что строим сначала, кто пользуется, какое правило реализуем и как проверяем пользу.

## P02 · Архитектура, модель данных и серверные контракты

PROMPT BEGIN P02

Спроектируй архитектуру SALON OS по P00 и утвержденному PRD. Клиентская и административная части используют единый домен; исходные данные и полномочия не дублируются в независимых приложениях.



Выбери архитектуру, соответствующую нагрузке и размещению. Начальная гипотеза — модульный монолит с PostgreSQL и worker. Покажи границы модулей, синхронные команды, фоновые события и внешние адаптеры. Микросервисы вводи при конкретном обосновании. Зафиксируй источник истины каждого домена: наша CRM для записи/клиентов; ручные зарегистрированные факты расчета в первом релизе; внешние касса и бухгалтерия. Платежного gateway первого релиза нет; не проектируй его как обязательную зависимость.



Минимальные сущности:

Tenant, Branch, LegalEntity/Seller, User, Membership, Role/Permission/Approval;

Client/ServiceRecipient, Contact, Representative, ConsentVersion, ClientDocument;

Staff, Qualification, Schedule, ScheduleException, Service/ServiceVersion, PriceRule;

Resource, Appointment, AppointmentItem, ServiceStepDefinition, StepDependency, VisitStep, ParallelCompatibility, ResourceAllocation/AllocationLink, BookingHold, VisitExecution;

Order/OrderLine, PaymentIntent, PaymentAllocation, Refund, Receipt, CustomerObligation, Certificate, Package, Redemption, LoyaltyTransaction;

Expense/ExpenseAccrual, CashAccount, CashMovement, Budget, Payable, PayrollRuleVersion, PayrollAccrual, PayrollApproval, Payout;

Product, Unit, Batch, StockMovement, Consumption, PurchaseOrder, ToolKit, ProcessingCycle, Equipment;

Complaint, Rework, Task, MessageThread, Campaign;

IntegrationConnection, ExternalMapping, ImportRun, WebhookInbox, ReconciliationRun, OutboxEvent, NotificationJob, DeliveryAttempt, AuditEvent.



Укажи связи, обязательность, область tenant/branch/seller, версии, индексы, уникальность и ограничения. Не допускай ссылку между объектами разных арендаторов. Внешний ID уникален внутри подключения, филиала и типа сущности. Глобальный аккаунт клиента не делает клиентские данные общедоступными всем салонам.



Для каждого изменяющего контракта опиши: полномочия, входную схему, серверную валидацию, состояние до/после, транзакцию, ключ повтора, ошибки и события. Для поиска/экспорта/файлов отдельно проверь область доступа. Генерируй API/OpenAPI из фактической реализации, а не выдумывай методы сторонних сервисов.



Создай машины состояний для записи/hold, выполнения, ресурса, платежа, возврата, чека, расхода, начисления, кампании и миграции. Опиши разрешенные переходы, повтор, конфликт и исправление. Учти частичную услугу и оплату, поздний платеж, отсутствие webhook, закрытый период.



Время — абсолютный момент плюс часовой пояс филиала; расписание задается локальными правилами. Деньги — точные суммы с валютой и политикой округления. Снимки условий и финансовые корректировки сохраняют прошлое. Не выполняй длинные сетевые операции внутри блокировок БД.



Результат: 03-domain, ERD, state diagrams, миграции, серверные контракты, решения 09-decisions. Приемка: модель объясняет полный визит и все независимые состояния; критические инварианты обеспечены ограничениями и транзакциями.

УТОЧНЕНИЕ ЭТАПА 1: нет приема денег клиентов платформой и нет AI-модуля. Визит, ручная регистрация оплаты и подтверждение внешнего чека остаются отдельными объектами. Сущности online PaymentIntent/Webhook нужны только включенному будущему адаптеру; не добавляй пустой платежный сервис в запуск.

ПОДТВЕРЖДЕННЫЕ КОПИИ: каждый салон имеет выбранную отдельную ветку/проект и изолированные базу, файлы, секреты и резервные копии. Кабинет платформы хранит реестр инсталляций/лицензий/версий/статусов. Для каждой копии явно укажи доверенные идентификаторы инсталляции и подключений; операторский обзор не становится общей CRM всех посетителей. Раздели data plane салона и control plane оператора.

Техническая база берется из PRODUCT_CONFIG: Next.js/TypeScript, PostgreSQL/Drizzle, отдельный worker/outbox/pg-boss. SQL-ограничения занятости добавляются настоящими миграциями, а не обещанием ORM. Managed PostgreSQL должен поддерживать необходимые расширения/DDL; проверь это перед выбором конфигурации. Собственная CRM является источником истины записи; банк/ККТ остаются внешними без выдуманного подтверждения.

## P04 · Организации, авторизация, права и кабинет оператора

PROMPT BEGIN P04

Реализуй основу доступа SALON OS по P00 и RBAC. ПОДТВЕРЖДЕНО: отдельная Git-ветка и копия проекта для каждого салона. Каждая инсталляция имеет собственную БД/учетные данные, секреты, очередь, конфигурацию, файлы и резервные копии. Бизнес, филиал, юрлицо-продавец, сотрудник, авторизационный аккаунт и человек — разные объекты. Общая инфраструктура при небольшом бюджете не отменяет логическую изоляцию и имеет описанный риск общего простоя.



Роли: владелец, управляющий, администратор, мастер, бухгалтер, склад/закупки, качество/наставник, обработка инструментов, клиент, оператор платформы. Совмещение ролей возможно; интерфейс показывает рабочий режим. Права задаются действием и областью: просмотр/изменение, контакты, финансы, скидка, возврат, зарплата, экспорт, чувствительные документы. Проверяй каждую серверную команду, файл, поиск и экспорт.



Используй поддерживаемую библиотеку серверных сессий; исходная рекомендация Better Auth. Гостевая запись без отдельной регистрации: обязательное подтверждение телефона при подтверждении брони. Телефон подтверждает управление контактом, не личность всех людей с таким номером. Не объединяй импортированные истории автоматически. Account, Person и семейный контакт связываются разрешенным процессом. Приглашения сотрудников ограничены ролью/филиалом, имеют срок, однократность и отзыв; чувствительные действия защищены усиленной проверкой/MFA. Отзыв членства прекращает новые действия старой сессии.



Контекст инсталляции/филиала подтверждай на сервере. Значение ID не является разрешением. Ограничения действуют в API, БД, кеше, файлах, экспорте, очереди и realtime. Пользовательские токены инсталляции A не работают в B. Не разрабатывай собственную криптографию и не раскрывай чужие аккаунты сообщениями ошибок.



Отдельный кабинет оператора входит в первый релиз. Он содержит реестр салонов/веток/версий/миграций/конфигураций, лицензии или договорные статусы и минимальные технические health-сигналы. Коммерческие планы/trial/счета реализуй после определения модели продажи; деньги за наш продукт отделены от расчетов клиентов салона. Не передавай в реестр телефоны, визиты, зарплаты и тексты ошибок с персональными данными. Поддержка получает ограниченный по времени доступ с основанием и аудитом. Поведение при недоступности лицензирования/grace/read-only явно задано; собственные данные и экспорт салона не блокируются неожиданно.



Создание новой копии воспроизводимо из базового шаблона, без данных и секретов действующего салона. Реализуй вход/приглашение/выход/восстановление, server authorization, матрицу ролей и настройки. Приемка: мастер видит разрешенных клиентов и свои начисления; администратор не меняет чужие ставки; A не читает объекты/файлы/поиск/export B; удаленный сотрудник не продолжает работу старым доступом; оператор не получает скрытый общий CRM.

## P05 · Каталог, графики и надежный движок записи

PROMPT BEGIN P05

Реализуй серверный движок записи SALON OS. Его используют публичный сайт, администратор и лист ожидания. По ответу пользователя источник истины — собственная система, последовательные и параллельные услуги нужны сразу. Источник истины записи — собственная БД; внешняя CRM используется только для согласованного переноса данных.



Услуга имеет версию, варианты, цену fixed/from/estimate, длительность, категорию специалиста, необходимые навыки, этапы, ресурсы и буферы. Цена и время могут различаться по мастеру/точке/сложности. Клиентские ответы помогают выбрать вариант, но неизвестное состояние не превращается в гарантированную цену.



Доступный слот — пересечение рабочих часов филиала, смены и исключений мастера, квалификации, времени всех этапов, доступности места/кабинета/аппарата и подготовительных интервалов. Время выдержки отдельно занимает нужные ресурсы; не освобождай руки мастера без разрешенного протокола. Последовательные/параллельные услуги и несколько исполнителей задаются явно. Неразрешенная параллельность запрещена. Ресурс с вместимостью >1 моделируется отдельно.



Для собственного источника используй защищенное БД резервирование. Для вместимости один применимы диапазоны времени и exclusion constraints; соседние интервалы [start,end) допустимы. Все назначения визита создаются атомарно. Повтор команды возвращает прежний результат. UI-проверка до сохранения недостаточна. Истечение hold — сохраненный переход, не индекс с меняющимся now().



Удержание для OTP, подтверждение, прибытие, отмена и неявка различаются. Срок удержания настраивается; покажи дедлайн. Состояние ожидания платежа и обработка поздней оплаты относятся только к будущему расширению и не включаются в первый релиз. Перенос берет новые назначения и освобождает старые в одной операции; если новое время не удалось, прежняя запись сохранена. Изменение услуги пересчитывает время/цену/ресурсы и требует согласования.



После принятого переноса прежняя CRM не остается вторым источником редактирования записей. Если позже пользователь отдельно запросит постоянную синхронизацию, ее авторитетные правила/конфликты/сверка проектируются как новое расширение.



Результат: каталог/версии, графики/исключения, поиск слотов, hold/create/move/cancel, журнал. Приемка: конкурентные запросы на последнее место дают одну бронь; конфликт второй услуги откатывает весь визит; мастер без навыка не предлагается; 45 минут+15 подготовки не помещаются в 50; отмена освобождает нужные ресурсы без потери истории.

ЭТАП 1: без предоплаты и платежного hold. Обязательное подтверждение телефона использует краткое атомарное удержание записи с отдельным сроком, а не сценарий оплаты. Время OTP/подтверждения не должно позволять нескольким клиентам занять последний ресурс. Будущая предоплата описана в общем контракте и реализуется только после включения.

ПАРАЛЛЕЛЬНОСТЬ ПЕРВОГО РЕЛИЗА: моделируй граф этапов и зависимостей без циклов, допустимость совместного выполнения и доступную позу/место клиента. Наличие двух свободных мастеров не делает любые процедуры совместимыми. Один клиент не находится одновременно в разных кабинетах. Общий ресурс нескольких перекрывающихся этапов того же визита резервируется единой занятостью со ссылками на этапы, без самоконфликта и без разрешения чужому визиту занять его. Время рук специалиста и технологического ожидания разделено по протоколу.

Объединять можно только один конкретный экземпляр ресурса, технологически разрешенный к совместному использованию данным клиентом/этапами. Если параллельным процедурам нужны два аппарата или два комплекта, потребность суммируется и резервируются разные экземпляры. Правило совместного использования не отменяет количество и пригодность.

## P06 · Клиентский сайт, гостевая запись и личный кабинет

PROMPT BEGIN P06

Реализуй клиентскую часть SALON OS по P00/P05. Пользователь подтвердил гостевую запись без предварительной регистрации и оплату в салоне. Не добавляй обязательный пароль, онлайн-эквайринг, предоплату или экран банковской карты в первый релиз.



Публичный сайт салона: услуги/варианты и понятные цены, мастера и реальные навыки, разрешенное портфолио, филиалы/адрес/часы/контакты, маршрут, FAQ и правила. Контент не должен быть выдуманными отзывами или фотографиями. Для брендовых инсталляций используй конфигурацию. Публичные страницы индексируются по согласованной SEO-структуре; персональный кабинет защищен авторизацией, а не только robots.txt.



Путь: выбрать филиал → одну/несколько услуг → мастера или любого подходящего → выполнимую последовательную/параллельную комбинацию → время → имя/контакт/необходимые условия → подтверждение телефона → подтвержденный визит. Если пользователь выбрал готовые комплексы, они являются тем же проверенным сервером графом работ. Не показывай невозможный «маникюр+педикюр», если нет двух подходящих исполнителей/мест.



Не запрашивай лишние поля. Показывай начало/окончание всего визита, порядок/пересечения услуг, мастеров, цену fixed/from/estimate и «Оплата в салоне». Доплата после консультации согласуется отдельно. Если услуга требует подготовки или предварительного условия, объясни это до подтверждения и предложи консультацию при необходимости.



OTP должен реально проверять контакт выбранным провайдером: срок, число попыток, частота, привязка к сценарию и защита от перебора. Если провайдер не подключен, допустима изолированная демо-авторизация с видимой пометкой; не объявляй телефон подтвержденным в live. OTP обязателен при подтверждении публичной записи, без отдельной регистрации: это подтвержденный ответ пользователя. Административная запись в салоне имеет собственное полномочие/правило и не использует фальшивое подтверждение телефона. Повтор страницы восстанавливает текущий серверный статус, а не создает дубли.



Кабинет: будущие/прошлые визиты, перенос/отмена по правилам, повтор с актуальными ценами, история зарегистрированных оплат и чеков, рекомендации, сертификаты/пакеты/остатки, документы и обратная связь. Покупки сертификатов в первом релизе оформляются в салоне. Нет кнопки «Оплатить онлайн». Клиент видит «возврат согласуется/оформлен салоном», а не неподтвержденный банковский успех.



Аккаунт, получатель услуги, представитель и плательщик разделены. Общий номер не открывает историю другого взрослого. Семейный/групповой доступ включается по правилам. Запись другого человека не доказывает полномочия читать его данные.



Приемка: мобильная запись без установки приложения; один последний слот не подтверждается дважды; ошибка OTP сохраняет выбор; неуспешный перенос сохраняет старый визит; повтор использует новые цены; отключение рекламы не блокирует необходимое сообщение о записи. Путь доступен с клавиатурой и читаем при ошибках/медленной сети.

При подборе нескольких услуг покажи совместимые готовые варианты, если свободная комбинация дает слишком сложный выбор. Система проверяет техническую совместимость для одного получателя, а не только наличие исполнителей.

ОБА ПУТИ ПОДТВЕРЖДЕНЫ: готовые комплексы и подбор совместимого общего визита из отдельных услуг доступны вместе. OTP доказывает контроль номера, а не личность всех людей, связанных с номером. Не привязывай импортированную историю другого взрослого автоматически; смена номера и получение доступа к прошлой карточке требуют безопасного отдельного процесса.

## P07 · Администратор: календарь, прием, закрытие и задачи

PROMPT BEGIN P07

Реализуй рабочее место администратора SALON OS. Цель пользователя — удобная запись и экономия времени. По умолчанию меню: Запись, Клиенты, Диалоги, Касса, Задачи. Финансы владельца, чужие зарплаты и массовый экспорт не появляются без отдельного права.



Календарь: день/неделя, мастера или помещения, фильтры, занятость ресурсов, буферы, параллельные услуги, задержки, отмены и лист ожидания. Перетаскивание имеет альтернативу через форму и подтверждает новое время сервером. Показ отдельного мастерского этапа не скрывает общий визит. Поиск свободного времени учитывает все ресурсы и навыки.



Карточка визита открывается без потери календаря. Обычная запись требует клиента, услуги, времени и исполнителя; дополнительные данные появляются по необходимости. Администратор видит прибытие, готовность места/материалов/инструментов, план услуги, согласованную цену, задержку и следующее действие. Не смешивай «пришел» с «услуга выполнена».



Сделай короткое действие «Закрыть визит». Состав и итоговая сумма берутся из согласованных строк. Минимальные дополнительные поля — фактически полученная сумма, способ расчета и при необходимости исключение. Если выбранное пользователем поведение использует умолчания, кнопка явно означает подтверждение соответствующих фактов. Она атомарно сохраняет результат выполнения и ручную оплату, но не проводит деньги через банк, не выпускает кассовый чек и не означает выплату зарплаты.



Исключения: недоплата/долг, частичная услуга, доплата, сертификат+карта, жалоба, отсутствие нужного материала, задержка, болезнь мастера. Администратор получает короткий исполнимый вариант действий и эскалацию в пределах прав. Известные поля не вводятся повторно. Материалы: нормы заполнены, отклонение или подтверждение мастера видны; не заставляй администратора измерять каждый тюбик при расчете.



Диалоги первой версии — люди и задачи, без ИИ. Подключенный канал, ответственный, статус и связь с записью сохраняются. Если канал не подключен, ручное обращение является честным ручным вводом. Назначь незавершенные обещания, платежи и обращения при передаче смены.



Приемка: администратор проходит прием и расчет одного визита коротким путем; двойной клик не дублирует оплату/начисления; неуказанная оплата не превращается в «полностью оплачено»; ошибка второй услуги не создает полувизит; права ограничивают скидку/возврат; передача смены сохраняет незавершенные задачи.

ПОЛЯ ЗАКРЫТИЯ ПОДТВЕРЖДЕНЫ: сумма, способ оплаты, фактические материалы и начисления мастерам. Нормы и расчет по правилам уже заполнены; мастер/админ меняет только отклонение. Администратор видит предварительный расчет и источник, а правка суммы начисления требует права/причины и не утверждает месячную ведомость. Поддержи несколько строк способов расчета за одной короткой формой.

## P08 · Мастер: услуга, техническая история и быстрый факт

PROMPT BEGIN P08

Реализуй мобильное рабочее место мастера SALON OS: Мой день, Мои клиенты, Материалы, Мои начисления. Мастер видит назначенных клиентов, необходимые сведения и свои деньги. Контакты, экспорт и чувствительные документы доступны только по правам.



Экран «сейчас»: клиент, нужная история, услуга/этап, согласованный план, длительность, ресурсы, подготовка и действие. Предыдущая техническая карта помогает продолжить работу, но новая формула не перезаписывает старую. Нужны предпочтения, разрешенные фото, фактическая формула/материал, рекомендации и дата следующей услуги; поля зависят от специализации.



Фиксация: начать/приостановить/завершить этап, отметить фактическую услугу и время. При дополнительном объеме покажи изменение цены/времени/расхода и согласование клиента. Пересчитай влияние на следующие записи. Мастер не добавляет скрытую доплату после завершения.



Расход максимально прост: заранее заполненные нормы, одно действие подтвердить расход по норме либо изменить отклонение/причину. Храни кто подтвердил факт. Оценка автоматически не становится измеренным фактом. Для колористики возможен быстрый ввод порции/формулы; ногтевому мастеру эти поля не показываются.



При параллельном визите каждый мастер завершает свои работы, а общая запись сохраняет зависимые этапы. Вознаграждение может распределяться по конкретной позиции/доле, не по полному чеку всем исполнителям. «Завершить услугу» передает администратора на расчет, а не автоматически отмечает клиента оплатившим.



Черновик сохраняется, конфликт редактирования виден. При потере сети интерфейс показывает несохраненный локальный черновик/режим чтения; после восстановления сравнивает версию сервера. Не обещай подтвержденные изменения расписания/денег offline. При logout/отзыве доступа защищенные данные устройства очищаются по политике.



Начисления: предварительно/утверждено/выплачено; переход к услуге, версии правила, базе и корректировке. Не показывай необъяснимую сумму и не трактуй недостачу как вину сотрудника.



Приемка: мастер фиксирует обычную услугу быстро с телефона; допуслуга имеет подтверждение; повтор сохранения не удваивает расход; частичная работа сохраняет факт материалов; другой мастер не читает чужую закрытую информацию; уход специалиста не уничтожает необходимую клиентскую историю салона.

PROMPT END P08



## P09 · Оплата в салоне, кассовый учет, сертификаты и возвраты

PROMPT BEGIN P09

Реализуй расчет SALON OS в подтвержденном режиме пользователя: клиент платит непосредственно салону; платформа не принимает, не распределяет и не возвращает его деньги. Администратор фиксирует внешний расчет и закрывает визит. Онлайн-предоплата/эквайринг — отдельное будущее расширение, выключенное в первом релизе.



Услуга выполнена, оплата отмечена и чек подтвержден — разные факты. Счет составлен из согласованных услуг/товаров и корректировок. Ручная платежная запись хранит сумму, валюту, способ, салон/продавца/кассу, время фактической операции, автора, источник manual и связь с позициями. Поддержи наличные, терминал/карта, иные разрешенные способы, частичный расчет и неоплаченный остаток.



Кнопка «Закрыть успешно» не скрывает неизвестные значения: итог виден, способ задан явно или согласованным умолчанием, полученная сумма подтверждена администратором. Двойной клик идемпотентен. Ошибка сохранения не показывает успех. Долг или невыполненная позиция оформляются отдельным понятным состоянием. Мастерские начисления не получают статус «выплачено» при оплате клиента.



Без кассовой интеграции приложение не создает фискальный чек. Покажи «чек не подтвержден» или «выдача во внешней кассе отмечена сотрудником» и при наличии внешний номер/документ. Не называй ручную отметку проверкой кассы. Вопросы применимости ККТ и реквизитов решает конфигурация страны/продавца.



Сертификат/пакет: отдельно продажа в салоне, покупатель, получатель, полученные деньги, номинал/право, область применения, остаток, погашение и возврат. Сумма погашения блокируется атомарно; два администратора не тратят один остаток. Номинал проданного со скидкой сертификата не равен поступлению денег. Бонусы/промокоды имеют другие правила.



Возврат в MVP — решение уполномоченного человека и регистрация фактически оформленного салоном возврата. Статусы запрос/утверждено/оформлено/отклонено различаются. Сумма и способ связаны с исходным расчетом; исправления сохраняют историю. Денежный возврат не отменяет факт услуги и расход материалов.



Если онлайн-платежный модуль включат позже, отдельно реализуй официальный контракт провайдера: сохраненный ключ повтора, server verification, ожидание, webhook inbox, неизвестный результат, позднюю оплату и фискальную сверку. Не добавляй его заранее в текущий путь.



Приемка: manual 6 900 ₽, 2 000 сертификатом и 4 900 картой дают нулевой остаток без online API; двойной клик не удваивает деньги; частичный возврат не превышает исходный расчет; обещание возврата не показано как фактическая выплата; внешний чек честно обозначен.

СМЕШАННЫЙ РАСЧЕТ: одна команда закрытия сохраняет отдельные строки методов и распределение по позициям/продавцам. Защищай не только повтор command_id, но и повторное закрытие уже обработанного визита другим command_id через состояние/версию/уникальность. Исправление — корректировка, не новое случайное поступление.

Для сертификата со скидкой явно выбери управленческую политику распределения фактически полученного возмещения между погашенной услугой и оставшимся обязательством. Например, пропорциональное признание — проектная политика, а не универсальное налоговое правило. Возврат не возвращает номинал автоматически вместо фактической оплаты и не восстанавливает повторно то же право одновременно с денежным возвратом.

## P10 · Расходы, прибыль, деньги и обзор владельца

PROMPT BEGIN P10

Реализуй управленческие финансы SALON OS. Пользователю нужны реальные расходы и понятная экономика. Учет салона отделен от SaaS-подписки, а ручная отметка оплаты — от банковской сверки. Согласуй учетную политику, вместо неявного выбора «все оплаты = прибыль».



Расход: статья, организация/филиал, контрагент, сумма/валюта, дата возникновения, дата/статус оплаты, счет/касса, документ, повторение, ответственный и утверждение. Нужны аренда, коммунальные услуги, связь, маркетинг, расходные материалы, обслуживание, обучение, персонал и другие статьи. Закупка запаса, оборудование, погашение займа, внесение капитала и изъятие владельца не превращаются автоматически в расход выполненных услуг.



Разделяй:

выручку по учетному правилу;

переменные расходы;

маржинальный доход;

задолженность/платежи;

обязательства по авансам, сертификатам и пакетам.

Планирование: платежный календарь, бюджет, обязательства, повторяющиеся расходы, риск нехватки денег и сценарии цены/штата. Сценарий не является фактическим эффектом. Общие расходы распределяются явным методом; труд работающего владельца и стоимость замещения показываются отдельно. При неполных расходах результат — предварительный.



Сверка первой версии: ручные суммы кассы/терминала/банка, источники, расхождения и отчет. Импорт банка возможен отдельным адаптером, но отметка сотрудника не называется подтверждением банка. Закрытие смены/периода и корректировка имеют права, причины и историю.



Обзор: выбранные период/филиал/юрлицо, полнота данных, выручка, результат, деньги, обязательства, полезная загрузка и не более нескольких приоритетных действий. Из каждого отклонения можно перейти к визитам, расходу, начислениям и источникам. Разрезы — услуга, ресурс/час, мастер, клиентская когорта, канал и точка при сопоставимых определениях.



Приемка: аванс/сертификат не удваивает выручку при погашении; закупка материала влияет на деньги и запас, а факт расхода — на услугу; неоплаченная выполненная услуга сохраняет задолженность; закрытый период меняется корректировкой; отсутствие данных не заполняется демо-прибылью.

Если номинал сертификата отличается от суммы продажи, показывай остаток номинального права и денежное обязательство по принятой политике отдельно. Объясни распределение при погашении/возврате; не подписывай выбранный управленческий метод как универсальное налоговое правило.

## P11 · Команда, смены, зарплаты и прозрачные выплаты

PROMPT BEGIN P11

Реализуй команду и начисления SALON OS. Пользователь подтвердил поддержку процента, фикса за услугу, оклада/гаранта и сочетаний уже в первой версии. Точные формулы, форма сотрудничества и правомерность удержаний уточняются для салона.



Команда: сотрудник/исполнитель, договорная модель, услуги, заявленные и подтвержденные навыки, допуск/наставник, график/исключения, адаптация, условия предложения и даты действия. Плановая смена и фактически отработанное время разделены. Вакансия связывается с необслуженным спросом, мощностью и стоимостью, но решение принимает руководитель.



Правило начисления версионируется: получатель, событие возникновения, период, база, ставка/фикс, порядок скидок/материалов/налогов, категории/приоритет, округление, гарантия, бонус, переделки и возвраты. Уже примененная версия не редактирует прошлое. Пользователь заранее выбирает, когда начисление возникает: выполненная услуга, полученная оплата или другое договорное событие.



Различай гарантию как минимум и гарантию как дополнительную выплату. Пример минимума: рассчитано 9 000, минимум 10 000 → доплата 1 000, итог 10 000. Для процента после скидки и материалов: (3 000×0,9−500)×0,4=880; если согласован порядок «материалы, затем скидка»: (3 000−500)×0,9×0,4=900. Формула и выбранный порядок видны в расчетном листе. Налоговые ставки — настройка, а не жесткая константа.



Несколько исполнителей: начисление относится к конкретным строкам/этапам/долям; весь чек не начисляется каждому случайно. Фикс за смену, оклад, процент и гарант имеют понятное сочетание. Частичная услуга, скидка, пакет, сертификат, товар, консультация и гарантийный визит проходят отдельные правила.



Предварительный расчет, утвержденная ведомость и фактическая выплата независимы. Закрытие визита дает основания начисления, не выплату. Самозанятый/подрядчик/арендатор и штат не объединяются одним юридическим результатом. Статус/чек подрядчика и основания удержаний учитываются по модели страны. Возврат клиенту не означает автоматическое удержание у мастера.



Мастер видит свои суммы и переход к исходному визиту/правилу/корректировке. Бухгалтер экспортирует составляющие, обязательства и выплаты. Пересчет закрытого периода создает утвержденную корректировку с причиной. Болезнь/уход сотрудника перераспределяет визиты по навыкам и отзывает доступ, сохраняя историю.



Приемка: новая ставка не меняет прошлую ведомость; дата предоплаты не подменяет выбранное событие начисления; гарант не складывается дважды; два мастера не получают каждый полный процент; двойное закрытие визита не дублирует расчет; ручная выплата не меняет сумму начисления без основания.

Для сочетаний оклад/переменная часть/гарант обязательны формула, область гаранта (весь заработок либо переменная часть), период (смена/месяц), неполный период и порядок иных выплат. Пример: оклад8 000, переменная9 000, гарант10 000: max(оклад+переменная,гарант)=17 000; оклад+max(переменная,гарант)=18 000. Правило выбирается явно и показывается сотруднику.

## P12 · Материалы, закупки, оборудование и готовность инструментов

PROMPT BEGIN P12

Реализуй ресурсы SALON OS с приоритетом удобства администратора. Детальная модель работает в фоне, а обычный сотрудник видит понятные остатки, готовность и исключения. У пользователя нет требования вводить сложную складскую форму после каждого визита.



Материал: название/SKU, базовая единица, упаковка, проверенный коэффициент, поставщик, партия, срок/дата открытия, пригодность и метод стоимости. Граммы и мл не равны по умолчанию. Техкарта услуги имеет версию и плановый расход. При обычном визите норма заполнена; мастер/администратор подтверждает расход по норме либо меняет отклонение с причиной. Оценка и подтвержденный факт обозначены раздельно.



Операции: приход, приемка, перемещение, потребление, отход, инвентаризационная корректировка, возврат поставщику. Они имеют автора, дату, единицы, стоимость и связь с визитом/партией. Факт 80 г вместо нормы 60 г дает расход 80, а не 140. Повтор сохранения не дублирует его. Новая закупочная цена не переписывает старый закрытый расход.



Отмена после попытки процедуры или денежный возврат не возвращают использованный материал в запас. Переделка учитывает новый расход. Отрицательный остаток/замена/неизвестная партия — явно заданное исключение с ответственным, а не незаметная подмена. Расхождение запускает проверку единиц, тары, расхода и стоимости; не обвиняет мастера автоматически.



Закупка: потребность по будущим услугам и истории, пригодный остаток, ожидаемое поступление, срок поставки, резерв и предложенный заказ/перемещение. Новый заказ утверждается по лимиту. Приемка сверяет количество, качество, цену, партию и срок; несоответствие превращается в претензию. Норма новой услуги обозначена как первоначальная оценка.



Оборудование/места: доступность, обслуживание, ремонт, резерв, ограничения, затраты. Неисправный аппарат исключен из расписания. Инструменты: комплект, стадии обработки, цикл, результат контроля, карантин, выдача и связь с визитом. Наличие комплекта не доказывает пригодность. Будущая плановая готовность и подтвержденная готовность непосредственно перед процедурой различаются. Нормативные требования проверяются для страны и услуги.



Интерфейс: «заканчивается/заказан/непригоден/расхождение», быстрый приход/инвентаризация, фильтр критических позиций. Специализация скрывает ненужные поля.



Приемка: комплект без результата контроля не готов; последний пригодный ресурс не резервируется дважды; ml не превращаются в g; факт не складывается с нормой; история цены сохраняется; повтор приемки не удваивает приход; возврат клиенту не увеличивает физический запас.

ПОДТВЕРЖДЕННЫЙ UX: нормы заполняются автоматически; мастер или администратор корректирует отклонение, отдельный закупщик ведет склад. При закрытии администратор видит итог фактического расхода/подтверждения по норме без сложного ввода всех партий.

## P13 · Качество, рекламации, переделки и передача ответственности

PROMPT BEGIN P13

Реализуй управление качеством SALON OS. Клиентская обратная связь, жалоба, техническая причина и финансовое решение связаны с исходным визитом, но имеют отдельные статусы и права.



Клиент может сообщить о результате из кабинета или через администратора. Решение: консультация, переделка, компенсация/возврат, отказ с основанием или иной согласованный вариант. Кто может обещать компенсацию и на какую сумму — полномочие салона. Переделка — отдельный визит со связью, причиной, объемом, дополнительными ресурсами/материалами, стоимостью дефекта и своим правилом вознаграждения. Исходный визит сохраняется. Возврат клиенту не является разрешением автоматически удержать деньги мастера. При неявке на переделку учитывается отдельное событие.



Анализ: повторяемость причин по услуге/партии/процессу, время ответа, фактическая стоимость, обучение, изменение протокола и контроль исполнения. Мастер с высокой долей сложных услуг не объявляется хуже только по сырому количеству жалоб. Статистика содержит период, базу и полноту.



Операционные задачи: открытие/закрытие, обещания клиенту, готовность ресурсов, незакрытые оплаты и обращение. Срок, ответственный, лимит полномочия, эскалация и передача смены видны. В отсутствие управляющего действует согласованный порядок. Повторяющиеся чек-листы не равны фактическому выполнению без подтверждения.



Если выявлен потенциально опасный материал/аппарат, допустимые действия определяются протоколом: непригодность/карантин, связанные визиты, проверка ответственным и связь с клиентами в утвержденном порядке. Приложение фиксирует факты и задачи, а профессиональное решение принимает человек.



Приемка: жалоба сохраняется при уходе мастера; переделка не теряет исходные расходы; незакрытая задача передана следующей смене; клиент не получает маркетинговую кампанию при открытой претензии по выбранной политике; исправление протокола создает новую версию.

## P14 · Повторные визиты, лояльность и проверка роста

Реализуй повторные визиты и рост SALON OS по P00. Приоритет первого релиза — полезная рекомендация, следующий визит и понятные сертификаты/пакеты. Расширенные автоматические кампании добавляй только в согласованный этап. ИИ в первой версии отсутствует.

Приемка: новый разработчик запускает staging по инструкции; обновление не ломает конфигурацию салона; копия реально восстановлена; сбой worker виден и исправим; real SMS не уходят из demo; deploy/rollback не удаляет финансовую историю. Исходный production-вариант: Timeweb Cloud SPB-3, Docker Compose, reverse proxy с TLS, управляемый PostgreSQL и private S3 в РФ.
