# P21 · Проверка готовности, пилот и финальная приемка

PROMPT BEGIN P21
Проведи независимую приемку SALON OS по P00, выбранному составу версии, 02-requirements, 08-acceptance и 33 INVARIANTS. Отложенные AI/online payment/medical не выдавай за реализованные. Их отсутствие в первом релизе соответствует ответам пользователя; проверяй только включенные контуры, а будущие сценарии помечай planned.

Для каждого requirement_id укажи implemented/tested/not enabled/blocked и доказательство: UI, серверный контракт, миграция, meaningful check. Проверь целый путь клиент → администратор → мастер → ручная оплата → расход → предварительное начисление → расходы/обзор → повтор. Красивые макеты и успешная сборка не доказывают рабочий день.

Обязательные группы проверки:
1. Клиент: гостевая запись, контакт, последовательность/параллельность, цена/время, перенос/отмена, история, сертификат/пакет, рекомендации/обратная связь.
2. Занятость: конкурентный последний слот, несколько ресурсов, буферы, навыки, два мастера, исключение смены, соседние интервалы, переход суток и неуспешный перенос.
3. Прием: пришел без услуги, частично выполнено, допуслуга/согласование, задержка, болезнь, недоплата, ручное закрытие и двойной клик.
4. Деньги: ручной cash/card, смешанный сертификат+карта, частичный возврат, неизвестный внешний чек, задолженность, закрытый период и корректировка.
5. Начисления: процент/фикс/оклад/гарант, дата правила/события, порядок скидки/расхода, два исполнителя, переделка, предварительно/утверждено/выплачено.
6. Материалы: единицы, факт вместо нормы, повтор, стоимость на дату, частичная попытка, отмена без физического возврата, пригодность/комплект.
7. Доступ: tenant/branch/seller, master/client contacts, export/files/search, старые сессии, приглашения и роль поддержки.
8. Надежность: уведомление после переноса, падение worker, повтор импорта, связь lost/offline draft, restore, отсутствие real действий из demo.
9. UX: узкий экран, клавиатура/фокус, ошибки/контраст/скринридер, скорость обычной операции и ясный следующий шаг.

Добавь расчетные проверки из 08-acceptance и воспроизводимые данные, а не тесты, копирующие внутреннюю реализацию. Для денег/доступа/гонок нужны интеграционные проверки с фактическими ограничениями/транзакциями. Отчеты о неисполненных тестах честные. Повторяй широкие проверки только если новая правка/ошибка оправдывает это.

Пилот: наблюдать реальные смены, ввод расхода, приемку, выплаты, переделку и работу без управляющего. Измерять время записи/закрытия, полноту фактов, необъясненные расчеты, ошибки/дубли, труд обучения и готовность продолжить. Экономический эффект отделять от обещаний и обычного спроса.

Финальный результат: рабочая версия/ссылка или честно описанный доступ, инструкция по ролям, состав функций, состояние интеграций, проверенные сценарии, оставшиеся блокеры с ответственным и следующий этап. Исправь критические ошибки до завершения. Не называй систему идеальной или production ready только по количеству экранов.
