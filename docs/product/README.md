# SALON OS: результат анализа и контекст проекта

Дата: 12 октября 2026 года.

## Что выполнено

Полный пакет Google Docs перенесен в текущий проект, разобран по продуктовым сценариям, архитектуре/данным и приемке. Исходный текст не сокращен. Три направления анализа выполнены параллельно и объединены основным агентом.

При первом осмотре C:/Users/User/Downloads/SalOS была пустой папкой, без кода и Git-репозитория. Созданы документация и снимок требований; приложение, БД, зависимости и внешние интеграции пока не создавались.

Текущий порядок задан пользователем: анализ/перенос → необходимые вопросы → пожелания → реализация после ответов. Пауза перед реализацией следует этому порядку; дополнительные согласования источником не вводятся.

## Главный результат анализа

Основания для первого демо уже достаточно определены. Не нужно повторно выбирать рынок, модель отдельных копий, гостевую запись, собственную CRM, параллельные услуги или способ приема денег. Неизвестными остаются конкретный показ, бренд/каталог, срок, окружение и пожелания.

P22 описывает работающий серверный продукт небольшого объема: клиент записывается → администратор принимает/переносит → мастер сохраняет выполнение/материалы → администратор закрывает → мастер видит объяснение начисления → владелец видит расходы/результат → клиент видит историю/права/обратную связь. Дополнительно нужен демонстрационный реестр копий.

Ключевые свойства: состояние сохраняется после перезагрузки; последний ресурс не бронируется дважды; повтор закрытия с тем же или новым ключом не создает дубли; нормы не суммируются с фактом; права проверяются сервером; OTP/уведомления/данные — только демонстрационные.

## Подходы к первому результату

| Подход | Соответствие ТЗ | Последствия |
| --- | --- | --- |
| Сквозное серверное демо P22 на вымышленном каталоге | Предпочтительный вариант по исходнику | Проверяет удобство и целостность, дает основу рабочей версии |
| Статичные экраны | Может помочь обсуждению дизайна, но не завершает P22 | Не доказывает запись/роли/расчеты/сохранение |
| Сразу полный live всех модулей | Возможен отдельным этапом после уточнений | Требует реальных правил, провайдеров, инфраструктуры, импорта и приемки |

Предварительная последовательность будущей реализации: общая серверная основа/модель → каталог/ресурсы/запись → администратор/мастер/закрытие → материалы/начисления/владелец → кабинет клиента/оператор → проверка и сценарий показа. Это порядок зависимостей, не окончательный план сроков. Он уточняется после ответов.

## Что нельзя потерять при реализации

1. **Данные и состояния:** запись, выполнение, ресурсы, расчет, чек, расход, начисление и выплата не подменяют друг друга.
2. **Запись:** совместимость процедур, граф этапов, навыки, буферы, место клиента и количество пригодных ресурсов проверяются атомарно в БД.
3. **Расчеты:** точные суммы, версии правил, долг, сертификат/обязательство, корректировки закрытого периода; ручная отметка не подтверждает банк или фискализацию.
4. **Доступ:** контакт/аккаунт/человек/представитель различаются; общий телефон не раскрывает чужую историю; оператор не получает общую CRM.
5. **Надежность:** outbox, бизнес-защита от повторов, отмена старых напоминаний, staging/сверка импорта, проверенный restore и реестр исправлений отдельных копий.
6. **Показ:** защищенный reset только demo; тестовый код никогда не проходит live; реальные внешние действия заблокированы.

## Несогласованности исходника и выбранная трактовка

- P03 говорит о шести статусах, I04 перечисляет семь независимых состояний. Сохраняем все состояния; число UI-бейджей не ограничивает модель.
- P15 ограничивает видимость тестовых кодов dev, P22 требует публичного DEMO-OTP. Предложен отдельный demo-адаптер, серверно недоступный live.
- A58 перечисляет ограничения бесплатной среды, P22 говорит о фактически выбранном окружении. Проверяем применимость, не приписываем другой площадке ограничения Render.
- PaymentIntent/Webhook из общего перечня P02 исключены его же уточнением этапа 1. Gateway не входит в первую версию.
- F01–F03 используются для разных наборов. В проекте ссылки уточняют раздел/пространство идентификаторов.
- Person и ручной расчет требуют единых имен в модели; синхронность закрытия и производных расчетов нужно закрепить контрактом.

Эти трактовки — аналитические технические выводы, а не новые пользовательские бизнес-правила. Подробные основания сохранены в отчетах.

## Границы проверки

Проверены полнота переноса и состав документа. Проверки приложения не запускались: приложения нет. Сценарии A01–A59 сохранены как будущие требования.

Внешние 60 страниц, Figma/ FigJam, актуальные версии стека, тарифы, география сервисов и правовая применимость не проверены. В проект перенесены ссылки и исходные описания, без утверждения об их актуальности. Перед реализацией/подключением проверяются нужные первичные материалы по фактически выбранным компонентам.

Все вопросы о будущем ИИ/онлайн-предоплате/странах не блокируют демо и не задаются повторно. Вопросы реальных формул, продавцов, медицинских услуг, импорта и эксплуатации нужны перед live.
