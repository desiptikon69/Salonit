# Запуск SalonIt без контейнеров

Обновлено 14 октября 2026 года. Для публикации на Timeweb с бесплатным техническим доменом, Docker и установкой как приложения см. [инструкцию по деплою](deploy-timeweb.md). Используется Node.js 24 и отдельная PostgreSQL. Для локального демо предусмотрен `scripts/local-db.ts`; для сервера — установленная системная PostgreSQL. Бесплатное доменное имя само по себе не предоставляет сервер для Node.js и базы данных.

## Локальная среда

Следуйте [README](../README.md). Встроенный пакет запускает настоящий сервер PostgreSQL на `127.0.0.1:55432`, создает `salonit` и `salonit_test`, сохраняет данные в `.data/postgres`. Он предназначен для разработки, с заранее известными локальными реквизитами. Не открывайте этот порт в интернет. Останавливайте процесс штатно через Ctrl+C.

Если порт занят, сначала проверьте, не работает ли уже экземпляр этого проекта. Не удаляйте каталог данных для устранения ошибки запуска. Вместо встроенного пакета можно установить PostgreSQL отдельно, создать две базы и изменить адреса в `.env`.

## Сервер Node.js

Для Timeweb нужен тариф, позволяющий запускать постоянный процесс Node.js 24 и использовать PostgreSQL. Доступы и подходящий тариф в этом проекте не настроены; инструкция не подтверждает публикацию.

1. Подготовьте отдельного системного пользователя приложения, каталог выпуска и отдельную базу с владельцем, имеющим права на свои схемы. Администратор PostgreSQL устанавливает расширение `btree_gist` в этой базе.
2. Передайте серверные настройки через защищенный файл окружения или менеджер секретов. Задайте `DATABASE_URL`, уникальные `BETTER_AUTH_SECRET`, `INSTALLATION_ID`, точный HTTPS-адрес в `BETTER_AUTH_URL`, `TZ=Europe/Moscow`. Для рабочего запуска используется `APP_MODE=live`; демонстрационные реквизиты туда не переносятся.
3. Выполните `npm ci`, затем `npm run db:migrate`, чистую инициализацию и создание владельца по инструкции ниже, затем `npm run build`. Не запускайте `db:seed` и `db:reset` для рабочей базы. Демонстрационный вход не заменяет настройку рабочих учетных записей.
4. Запускайте приложение через менеджер процессов от непривилегированного пользователя. Для настроенного `output: standalone` скопируйте `public` в `.next/standalone/public`, а `.next/static` — в `.next/standalone/.next/static`. Команда запуска: `node .next/standalone/server.js`, переменные `HOSTNAME=127.0.0.1`, `PORT=3000`. Окружение передается менеджером процессов и не попадает в клиентскую сборку.
5. Поставьте nginx или другой обратный прокси с HTTPS перед `127.0.0.1:3000`. Ограничьте размер запросов и частоту обращений к входу/бронированию. В интернет открывайте только необходимые веб-порты; порт PostgreSQL оставьте закрытым.
6. Настройте автоматический перезапуск, журналирование без секретов и персональных данных, резервные копии и проверку доступности. Отдельный обработчик фоновых задач запускается после проверки его реализации и конфигурации в текущем выпуске.

Подключение реальной SMS-доставки, проверка входа по телефону, настройки согласий и первичных учетных записей обязательны до приема реальных клиентов. Отсутствующий SMS-провайдер должен приводить к явной ошибке; отображение демо-кода в рабочем режиме недопустимо. Онлайн-платежи не входят в этот запуск: оплаты учитываются как внешние ручные операции салона.

## Чистая установка и первый владелец

На новой базе сначала задайте отдельные `DATABASE_URL`, `INSTALLATION_ID` (3–80 латинских букв, цифр, `_` или `-`, первый символ — буква или цифра), `APP_MODE=live`, `BETTER_AUTH_URL` и случайный `BETTER_AUTH_SECRET`. Не копируйте `.env` демонстрационной установки. Затем выполните:

```text
npm run db:migrate
npx tsx scripts/init-installation.ts
```

Инициализатор работает только с пустой базой после миграций и выполняет изменения одной транзакцией. Повторный запуск отказывается изменять существующие данные. Создаются настройки с фактическим `APP_MODE`, техническая запись установки, шаблоны услуг, комплексов и ресурсов. Адрес, телефон и часы работы пусты. Услуги выключены; ресурсы недоступны до настройки. Ориентировочные цены и длительности шаблонов нужно проверить и заменить перед включением услуг. Нормы расхода очищены: настройте их по фактическим материалам салона.

Демонстрационные клиенты, сотрудники, остатки, визиты, платежи, начисления, учетные записи и секреты не создаются. Инициализатор не предназначен для обновления существующей установки.

Перед созданием владельца задайте `SALONIT_USER_PASSWORD` в защищенном окружении текущего процесса (12–128 символов). Пароль не передается аргументом команды. Подставьте настоящий адрес и имя:

```text
npx tsx scripts/create-user.ts owner@example.org "Имя владельца" owner
```

После выполнения удалите `SALONIT_USER_PASSWORD` из окружения оболочки или менеджера секретов, использованного для этой разовой операции. Команда не выводит пароль. Войдите через обычную форму входа по email и паролю. Заполните контакты, расписание, сотрудников, реальные цены, материалы, остатки и нормы; подтвердите готовность оборудования, затем включите услуги. Сотрудников с доступом создавайте той же командой с нужной ролью. Для роли `master` обязателен четвертый аргумент — идентификатор существующего активного сотрудника.

## Резервная копия

```text
npx tsx scripts/backup.ts
```

Сначала установите клиентские утилиты PostgreSQL: текущий пакет embedded-postgres не содержит `pg_dump`. Скрипт читает `DATABASE_URL`, передает пароль `pg_dump` через окружение дочернего процесса и сохраняет архив custom format в `.data/backups`. URL и пароль не попадают в аргументы команды или отчет. Используется `pg_dump` из PATH либо абсолютный `PG_DUMP_PATH`; предусмотрено обнаружение комплектной утилиты Windows, если она присутствует в другой версии пакета. Версия утилиты должна поддерживать версию сервера; старый `pg_dump` не снимает архив с более нового PostgreSQL. Локальная проверка 14 октября остановилась до подключения из-за отсутствия утилиты; архив и восстановление пока не проверены.

Архив содержит данные клиентов и учетных записей. Ограничьте доступ к каталогу средствами ОС, храните зашифрованную копию вне сервера, согласуйте срок хранения. Каталог исключен из Git. Скрипт не шифрует архив и не отправляет его наружу. Он сохраняет одну базу без владельцев и ACL; глобальные роли PostgreSQL, файлы и секреты нужно резервировать отдельно.

Проверяйте восстановление в новую пустую изолированную базу командой `pg_restore --no-owner --no-acl --exit-on-error --dbname=<имя-проверочной-базы> <путь-к-архиву>`, передав подключение через переменные `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`. После восстановления проверьте число записей, вход и операции приложения. Не направляйте проверку восстановления в рабочую базу. Создание файла архива без такого восстановления не доказывает восстанавливаемость.

## Копия для другого салона

Каждый салон получает отдельную базу, пользователя БД, секреты, домен, каталог файлов, резервные копии и идентификатор установки. Начинайте с чистой базы, миграций и `scripts/init-installation.ts`, затем отдельно создавайте владельца. Не копируйте клиентскую базу, сессии, OTP, платежи и демонстрационные учетные записи. Общие изменения кода переносите из базового проекта; индивидуальные настройки храните отдельно. В реестре оператора храните технические сведения об установках, а не объединенный список клиентов.
